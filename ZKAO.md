# zkao fork

This repo is a fork. `zkao` is our long-lived working branch; `main` tracks upstream releases. `zkao` is periodically rebased onto a new upstream release tag and released as `vX.Y.Z.zkao`.

Fork-specific docs live in this file only, so upstream files (`README.md`, `AGENTS.md`) stay as close to upstream as possible and rebases do not conflict on them.

## Commit layout

`git log --oneline vOLD..zkao` lists what the fork carries. Keep it small:

- One commit per feature. When a rebase needs an adaptation fix, fold it into the feature commit it adapts instead of adding an "adapt fork features to vX" commit: `git commit --fixup=<feature-sha>`, then `GIT_SEQUENCE_EDITOR=true git rebase -i --autosquash vNEW`.
- The fork docs commit (`docs: zkao fork maintenance`, this file plus the AGENTS.md pointer) is always the last commit. Each release amends it instead of adding a new commit.
- Drop commits upstream has absorbed. Prefer sending general fixes upstream so the fork shrinks over time.

## Backups

Before every rebase of `zkao` (including history rewrites such as squashing):

- Confirm uncommitted/untracked work is committed first; a backup branch only captures committed state.
- Create a backup branch named `zkao-v<version>-backup`, where `<version>` is the upstream release `zkao` is currently synced to (the newest `vX.Y.Z.zkao` tag: `git tag --sort=-version:refname | grep zkao | head -1`), not the rebase target. Push it to `origin`.
- Record it in the table below (branch name, synced version, date, what it preserved).

Keep backup branches around (do not delete them); they are our recovery point if a rebase goes wrong.

## Releasing a zkao version

A zkao release rebases our commits onto a newer upstream **release tag** and tags the result `vX.Y.Z.zkao`. It does **not** bump versions or publish to npm: the `.zkao` tag inherits the upstream `vX.Y.Z` package versions, and pushing it triggers `.github/workflows/zkao.yml`, which builds, packs each package's tarball, and creates the GitHub release with those `.tgz` assets. (The upstream "Build Binaries" workflow also fires on the tag and harmlessly fails; ignore it.)

Let `OLD` = the upstream release `zkao` is currently synced to (the newest `vX.Y.Z.zkao` tag: `git tag --sort=-version:refname | grep zkao | head -1`), `NEW` = the upstream release tag to move to (`git tag --sort=-version:refname | grep -v zkao | head`).

1. **Backup** (see [Backups](#backups)): from a clean tree, `git branch zkao-vOLD-backup zkao && git push origin zkao-vOLD-backup`.
2. **Rebase** our commits onto the new release: `git fetch upstream --tags` then `git rebase --onto vNEW vOLD zkao`. Resolve conflicts only in files we modified; **drop** any of our commits upstream has since absorbed. Fold any follow-up fixes into their feature commits (see [Commit layout](#commit-layout)).
3. **Verify**: `npm install --ignore-scripts && npm run build && npm run check`, then run the AI tests (`cd packages/ai && npx vitest run`). The build regenerates `*.generated.ts` from live APIs and `npm install` may touch `package-lock.json`; `git checkout -- <those>` before tagging so the tag matches the upstream `vNEW` tree.
4. **Record the backup**: add a `zkao-vOLD-backup` row to the table below (synced version, today's date, what the rebase dropped/re-resolved) and amend the last commit (`git commit --amend --no-edit -- ZKAO.md`).
5. **Tag and push** (lightweight tag, matching prior `.zkao` tags):
   ```bash
   git tag vNEW.zkao zkao
   git push origin vNEW^{commit}:refs/heads/main   # sync main (fast-forward to the release)
   git push --force-with-lease origin zkao         # rebased history
   git push origin vNEW.zkao                        # triggers the release workflow
   git branch -f main vNEW^{commit}                 # keep local main in sync
   ```
6. **Confirm**: `gh run watch <id> --repo zksecurity/pi-mono --exit-status` on the "zkao Release" run, then `gh release view vNEW.zkao --repo zksecurity/pi-mono` shows a non-draft release with a `.tgz` asset per published package.
